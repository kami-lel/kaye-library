# Kaye Library：组曲[Suite]与 Git 使用文档

[English](suite-git-usage-doc.md) | 简体中文

把大任务当作一个**组曲**来跑：先出计划，再拆成一个个可审阅的小步推进，随时可以暂停。建议先读*为什么*，再看文末的*示例*，那是一次完整的实战演示。

本文讲清了涉及的全部技能，包括组曲技能和所有 Git 技能，详见下面的[技能详解](#技能详解)；[技能目录](skill-catalog-doc.zh-CN.md#movement-与-suite)则是简明清单。

## 为什么

不用组曲、直接让 Kaye 做一次大改动，它往往一口气做完：改了 30 个文件，生成一个巨大的 diff，没法只收下其中一部分，会话一断，全部白做。

组曲[Suite]把**想**和**做**拆开，解决这个问题：

- **先出计划**：Kaye 先读你的仓库，写出一份计划文件。你批准之前，不会改任何东西。
- **小步推进**：每一步（一个**乐章**[Movement]）都是一个可单独审阅的单元，对应一次 git 提交，你可以逐步接受、驳回或调整方向。
- **进度落盘**：计划文件记录进度，今晚停下，明天接着干，换个会话也行。
- **多线并行**：互不相干的工作可以同时进行，交给只有 Kaye 参与的**声部**[Voice]去跑。

适合目标明确、跨多个文件、需要多轮完成的工作。一轮就能搞定的小改动，直接说就行。

## 术语

这些词在这里有特定含义，不是日常用法。

| 术语 | 在这里的含义 |
|---|---|
| **组曲**[Suite] | 整个大任务，记录在一份计划文件里；不是测试套件。通常 1 个组曲对应 1 条功能分支 |
| **乐章**[Movement] | 组曲里带编号的一步，粒度以能单独审阅、单独接受或驳回为准；不是界面动效。1 个乐章 = 1 次 git 提交 |
| **声部**[Voice] | 一条有序的乐章线。**主声部**[Main Voice]（🧩）由你审阅；**器乐声部**[instrumental Voice]（🎻 小提琴、🎺 小号、~）只由 Kaye 执行，在各自的分支上并行运行 |
| **计划文件** | 写下来的组曲，文件名为 `<task>-suite-plan.md`：既是计划，也是保存下来的进度，所以运行可以暂停、再恢复 |
| **逐章暂停**[Halt] / **连续推进**[Cascade] | 两种节奏：每个乐章做完就停下等你，或者一路做到整个组曲完成 |
| **重订计划**[Rework] | 现实跟计划对不上时，Kaye 先停下，改写计划，再请你批准；绝不绕过去硬做 |
| **关联工作树**[linked worktree] | 同一仓库额外检出的一个目录，每个任务一个，不影响你的主工作树 |

## 速记

聊天里可以用单个字母代替整句话：

| 输入 | 含义 | 效果 |
|---|---|---|
| `c` | 继续[continue] | 继续运行；在逐章暂停节奏下，开始下一个乐章[Movement] |
| `n` | 下一个[next] | 前进到下一个：下一个乐章或下一项 |
| `g` | 提交[git commit] | 只提交**本次对话里做的改动**，经由 `/commit-sense`；Kaye 没动过的改动原样保留，不确定就问你 |
| `gi` | 提交已暂存的内容 | 只提交**暂存区里已有的内容**，包括 Kaye 不知道的改动；工作区不动 |
| `ig` | 全部暂存，再提交 | 把工作区**所有**改动（包括未知的）都暂存到暂存区[index]，然后提交 |

*暂存区[index]*就是为下一次提交排队的改动。想提交 Kaye 做的活，用 `g`；自己手动 `git add` 过文件、只想提交那些，用 `gi`；想把目录里的改动一股脑全提交，用 `ig`。

## 技能详解

组曲[Suite]流程里的每个技能：做什么、何时触发。可以按名称调用（`/play-suite`），也可以直接说需求，Kaye 会自己选。组曲跑起来之后，大多数技能会自动触发。

### 做计划

#### `/plan-for-suite` 🌟

把过大的任务变成一份计划文件，然后等你批准。分 2 个阶段：

- **调研**：只读。Kaye 读入口、约定和任务会碰到的文件，弄清哪些已有、哪些做了一半、哪些缺失，遇到含糊之处（范围、优先级、取舍）就问你。在 Claude Code 里这一步处于计划模式，不可能改动任何东西。
- **写计划**：Kaye 把任务拆成带编号的乐章[Movement]，存到 `<task>-suite-plan.md`（工作区根目录，没有则放仓库根目录）。每个乐章记录它的**范围**[Scope]（涉及的文件，要写全，且尽量少）、**说明**[Statement]（做什么、为什么，一两句话）、**完成标准**[End State]、**执行方**[Party]（谁来做：Kaye、你，或其他人，按名字写）和**状态**[Status]（`Pending`）。

文件开头是一段固定的前言，告诉执行者先加载哪个技能；接着是 `## Context`、`## Terrain`（技术细节、相关文件、约束），需要时再加 `## Design`、`## Order`（依赖图，只在有声部[Voice]时出现）和 `## Rework`。乐章放在 `## Main Voice` 下，每个器乐声部[instrumental Voice]一个类似 `## 🎻 Violin Voice` 的标题。

杂务由 Kaye 根据仓库状态自行判断：

- 用 git 且有乐章要改已跟踪的文件时，用一个乐章创建**功能分支**
- 主工作树被占用，或你要求别动它时，用一个乐章创建**关联工作树**
- 收尾用一个乐章**合并**分支
- 只有当 3 个以上的乐章是只由 Kaye 完成的工作，且与其他声部没有共用文件时，才会开一个**器乐声部**。声部宁少勿多：每个声部至少 5 个乐章

在“做个计划”“拆成乐章”“一步一步来”时触发。不适用于一轮就能做完的任务。

#### `/rework-plan-for-suite`

处理计划与现实脱节的情况：出了 bug、假设不成立、某个乐章不对或多余、冒出计划外的工作、你改了方向，或恢复时工作区对不上。Kaye **立刻停下，绝不绕过去硬做**，然后：

1. 说明发现：计划的假设、实际情况、对后续乐章的影响
2. 整份重写计划（绝不只给 diff）；已完成的乐章原样保留，编号不变
3. 标出每个乐章的状态（`Pending`、`Done`、`Halted`、`Dropped`）
4. 绝不重新编号：被拆分的乐章保留原编号，下面加子乐章（`Movement 1.1`、`Movement 1.2`）
5. 把发现追加到 `## Rework`，按时间由旧到新，绝不改动此前的条目
6. 等你批准，然后从最早未完成的乐章继续

运行中随时触发，没人叫它也会触发。你也可以主动调用：“重新规划”“计划已经不适用了”。

### 动手执行

#### `/play-suite`

执行已批准计划的**主声部**[Main Voice]。Kaye 按顺序进入每个乐章，在它的范围内工作，直到完成标准成立，然后提交、小结，再把控制权交回给你。不会跳过，也不会合并；**你的话优先于顺序**，想跳着做、同时做几个、或者把计划搁在一边，都照办，不会争辩。

- **进度落盘**：计划文件就是这次运行的记忆。说一声 `pause`，每个状态都会写下来；恢复时 Kaye 从最早一个不是 `Done` 或 `Dropped` 的乐章开始，并先检查功能分支、器乐分支[instrumental branch]和关联工作树是否还在。
- **你自己的乐章**：执行方是你的乐章，Kaye 绝不替你做：它先说明目标，每次只给 1 个步骤，等你汇报，再通过你的确认或自己的检查来核实完成标准，并说明用的是哪种方式。
- **其他执行方**会拿到步骤和完成标准，Kaye 再核实对方的汇报。
- **进度追踪**：Kaye 的待办清单里，每个乐章占 1 条（包括所有声部），并标出当前这条。

在计划文件的前言、“开始”“继续”“暂停”“恢复”，或 `c` 时触发。

#### `/halt-each-movement` 与 `/cascade-all-movements`

主声部的两种节奏；开跑时 Kaye 会问你选哪种。

| | `/halt-each-movement` | `/cascade-all-movements` |
|---|---|---|
| 每轮 | 1 个乐章 | 剩下的全部乐章一轮做完 |
| 下一步 | 你说 `c` 或“继续” | 自动 |
| 何时停 | 每个乐章结束时 | 组曲完成，或某个乐章的执行方是你 |
| 提交 | 轮末把改动暂存到**暂存区**，你批准（`g`）后提交 | 每个乐章结束时提交 |
| 结尾 | `🎏` 完成行 + `🧭` 下一步行 | 每个乐章一条 `🎏` 行，最后 `🏁` |

两者使用同样的进度标记：`🎏 🧩3\7 …` 表示第 3 个乐章完成（共 7 个），`🧭 🧩4 …` 指出下一个，`🎌 …` 表示一个器乐声部已合并回来，`🏁 …` 表示组曲完成。在 Claude Code 里，连续推进必须停下等你时还会发一条推送通知。无论哪种节奏，器乐声部内部都不会停。

触发词：“一次一个乐章”“每步之间让我审阅”（逐章暂停）；“把所有乐章跑完”“一直做到组曲完成”（连续推进）。

### 声部

#### `/solo-voice`

从头到尾跑完 1 个**器乐声部**，只由 Kaye 执行，可以作为子智能体，也可以在独立会话里运行。主会话只告诉它计划文件和声部名，其余什么都不说；声部自己去读计划。它只在自己的关联工作树、自己的器乐分支上工作，每个乐章提交 1 次，**绝不向你提问，也绝不自行合并分支**。遇到与计划不符、完成标准无法成立的情况，它会停下并汇报。

它以 1 份汇报收尾：每个乐章的提交哈希和完成标准（已达成，或未达成的原因）、停在哪里、还剩什么。随后主会话把这条分支合并回功能分支，移除工作树，删除分支，并标上 `🎌`。默认用子智能体；声部太大、子智能体扛不住，或者你想全程盯着看时，才用独立会话。

只在被派发时触发；不用于主声部。

### Git 规则与提交

组曲会把工作树、合并和清理分支这些技能当作普通乐章来安排，并在该乐章的说明里写明所用技能；其余的会自动触发。组曲进行中，你几乎不用手动调用它们。

#### `/working-with-git`

约定 Git 工作用语和边界，让改动留在工作区、不妨碍你。Kaye 在 Git 仓库里工作时会自动加载。

- 改动写在工作区；Kaye 做完或做到一半时，把自己的改动暂存到暂存区；只有代码库状态与预期不符时才运行 `git status` 或 `git diff`
- **你可能在同一个目录里同时工作**：不是 Kaye 做的改动就视为你的，它绝不会还原、暂存或提交；如果挡了它的路，它会停下来向你汇报
- **必须由你在同一轮里明确点名**才会执行：改写历史（`commit --amend`、`rebase`、`reset`、`cherry-pick`）、丢弃工作（`reset --hard`、`checkout .`、`restore .`、`clean -f`、`stash drop`、`branch -D`）、发布（`push`、`push --force`、`tag`、`gh pr create`）、全量暂存或绕过检查（`add -A`、`add .`、`--no-verify`）
- 每次提交都走 `/commit-sense`，绝不自创提交信息格式

#### `/commit-sense` 🌟

提交暂存区里的 diff。提交信息取自对话内容，必要时用 `git diff --cached --numstat` 核对，然后提交一次。信息最多 3 部分：覆盖整个 diff 的**主摘要**、**文件清单**（每个文件：一个变更符号、文件名、一句话摘要；只有一个文件时只写符号和文件名），以及可选的 co-author 署名。

```text
restructure commit sense under Git hierarchy
🪧`CHANGELOG.md` remove stale TT
📖`http-api-doc.md` document commit-sense prompt nodes
🧪`__init__.py` update fixtures: heading levels
```

回复只有 1 行，例如 `🚩🐙 Commit a3f9c21`；Git 拒绝提交时，Kaye 会贴出报错输出并停下。在 `g`、“提交一下”、“写个提交信息”时触发。

#### `/commit-sense-branch-merging`

为进行中的合并写提交信息，只管信息本身：合并操作、合并提交、暂存区和工作区都归你。它会在 Git 自带的信息前加一行带类型的首行，Git 原文原样保留，并附上 co-author 署名。首行取决于涉及的分支：

| 从 | 到 | 首行 |
|---|---|---|
| 功能分支 | `dev` | `Feature Landing: BRANCH` |
| `dev` | 功能分支 | `Catch Up: BRANCH` |
| `dev` | `main` | 版本标题，例如 `Minor Release 1.1.0` |
| hotfix 分支或 release 分支 | `main` | `BUMP Hotfix Release VERSION` 或 `BUMP Release Cut VERSION` |
| hotfix 分支、release 分支或 `main` | `dev` | `Hotfix Backport from VERSION` 及同类 |

遇到没见过的分支组合会先问你，绝不瞎猜。在合并进行中触发：“写合并信息”。

#### `/resolve-merge-conflict` ⭐

处理被冲突打断的 `merge`、`rebase`、`cherry-pick` 或 `pull`。只改 Git 报告为未合并（unmerged）的文件，先结合上下文读懂双方的改动，再**按语义**调和：`import`、函数签名、配置项、调用处必须保持一致，两个分支的意图都要保留，绝不整块取 `ours` 或 `theirs`。lockfile 和生成的文件要重新生成，不手工合并；每个冲突标记都要清除，每个文件都要逐个检查；每解决一个路径就立即暂存。没把握的取舍交给你决定。

它只动工作区和暂存区：是继续还是放弃这次合并，由你决定。报告会逐文件列出双方各改了什么、怎么调和的、哪里需要再看一眼，最后说明暂存区已就绪，可以 `git merge --continue`。

### Git 工作树

**关联工作树**[linked worktree]是同一仓库额外检出的一个目录，固定在自己的分支上，所以一个任务里的改动不会影响另一个任务。每个任务（通常是一个组曲）有 1 棵工作树、1 条分支，绝不跨任务共用，也绝不切换到别的分支。唯一允许的拆分：每个器乐声部各有一棵自己的工作树。

```text
WS-kaye-library/
├── kaye-library/                              # 主工作树，在 dev 上
├── kaye-library-WT-add-search-filter/         # 关联工作树，功能分支
└── kaye-library-WT-add-search-filter-violin/  # 关联工作树，器乐分支
```

`WS-` 前缀标记存放多棵工作树的工作区目录；`-WT-` 标记关联工作树，命名为 `REPO-WT-BRANCH`。

#### `/tend-linked-wt` 🌟

管理一棵工作树的整个生命周期，从创建到移除。它会转交给下面 2 个技能，在开始、继续或结束某个关联工作树里的任务，或听到“别碰 main”时触发。

#### `/plant-linked-wt`

为任务已有的分支创建工作树；分支不存在时连分支一起创建：功能分支从它将要合并进去的分支（`dev`）切出，器乐分支从功能分支切出。

#### `/uproot-linked-wt`

**只有在其中每处改动都已提交，并已合并**进目标分支之后，才会移除工作树（功能分支合并到主工作树所在的分支，器乐分支合并到功能分支）。只要有一处不满足，就停下汇报。

### Git 合并功能分支

**功能分支**从 `dev` 切出，用来隔离地开发 1 个功能，完成后合并回去。命名以动词开头，不加 `feature/` 前缀：`add-search-filter`、`fix-token-refresh`。合并由 3 个技能依次完成；组曲的收尾乐章运行 `/land-feature`，由它去调用另外 2 个。

#### `/ready-land-feature`

合并前同步这条分支所影响的文档，分 7 个乐章：同步单元测试（如果有）、弄清这条分支交付了什么（对话、`git log dev..HEAD`、`[Unreleased]` 条目，仍不清楚就看 diff）、记进 `CHANGELOG.md`、让 `AGENTS.md` 和 `CONTEXT.md` 与之保持一致，最后提交这些工作。分支没影响到的文件不动。在“准备合并”“把我改的东西记成文档”时触发。

#### `/land-feature`

先做好准备（上面全部 7 个乐章），再用 `--no-ff --no-commit` 把分支合并到 `dev`，让合并提交保留这次合并的记录，并借着暂停的机会写好信息：`Feature Landing: BRANCH` 加一段简短的分支摘要。在关联工作树里工作时，合并要在主工作树里做，因为 `dev` 在那边。冲突交给 `/resolve-merge-conflict`。它停在合并提交这一步：推送和删除要等你批准，由 `/scrub-landed-feature` 来做。

#### `/scrub-landed-feature`

先报告合并结果，再请你批准最多 3 项，每项单独批准，因为推送是公开的，删除无法撤销：

```text
🚩🐙 功能已合并：add status filter to Search page
✍️ ⓑ 把 `dev` 推送到 origin？
✍️ ⓒ 删除功能分支 `add-search-filter`？
✍️ ⓓ 移除关联工作树 `kaye-library-WT-add-search-filter`？
ⓐ 以上全部
```

回答 `a` 表示全部，或者写字母组合，例如 `bd`。已批准的操作按 ⓑ、ⓓ、ⓒ 的顺序执行（Git 不允许删除仍被工作树占用的分支），删除用 `git branch -d`，绝不用 `-D`。

#### `/submit-pr`

先审阅再合并的另一条路：同样用 7 个乐章准备好文档，远程没有这条分支就先推送，然后运行 `gh pr create --base dev`，标题用分支摘要的标题行，正文用它的改动列表。PR 留给审阅者去合并，Kaye 回复它的 URL。

#### `/prune-merged-branches`

删除已合并到当前分支的本地分支，只用 `git branch -d`：被 Git 拒绝就认，分支保留。它会把待删候选和排除项一起列出，只要范围不明确（没说明的保护名单、看起来还在使用的分支）就等你回答。报告写明每条被删分支及其最新提交哈希，方便你找回，也写明每条被跳过的分支和原因。

### Git 发布版本

#### `/ready-release-version`

分 6 个乐章准备发布：

1. 确定版本号和日期（两者必需，缺了就问）
2. 更新 README 和 CREDITS
3. 更新 `docs/`
4. 精简 `AGENTS.md` 和 `CONTEXT.md`（改得更短，而不只是更新）
5. 收尾 CHANGELOG（精简 `[Unreleased]`，移入带日期的版本小节，留下新的 `[Unreleased]`，更新 compare 链接）
6. 在所有元数据文件里升级版本号（`pyproject.toml`、`package.json`、`Cargo.toml`、~）

#### `/release-version` ⭐

先做好发布准备（那 6 个乐章），提交这些工作，用 `--no-ff --no-commit` 合并到 `main` 并写上带类型的信息（`Minor Release 1.1.0`、~），给这次合并打上 `v` 加版本号的 tag，再交给清理阶段。在“发布 1.2.0”“发个版并打 tag”时触发。

#### `/scrub-released-version`

先报告发布结果，再请你批准最多 4 项：

```text
🚩🐙 Minor Release 1.1.0
✍️ ⓑ 把 `main` 和 `v1.1.0` 推送到 origin？
✍️ ⓒ 清理已合并的分支 `add-search-filter`、`fix-login-redirect`？
✍️ ⓓ 把 `dev` 快进（fast-forward）到 `main`，本地和 origin 都做？
✍️ ⓔ 把 `dev` 升到 `1.1.1-alpha`，本地和 origin 都做？
ⓐ 以上全部
```

下一个预发布版本号是已发布版本的补丁号加 1，再加上 `-alpha`，所以 `dev` 永远不会占用已发布的版本号。升版本号只在快进成功之后才做，并通过 `/commit-sense` 提交。

### 术语相关技能

这些配套技能负责承载术语和记法。宣布或展示组曲时，它们会自动加载。

- `/agent-movement-and-suite`：定义**组曲**、**声部**和**乐章**，规定粒度（每个乐章可审阅、边界清晰，在所属声部内从 1 开始编号）、声部的乐器顺序、与待办清单一一对应的追踪方式，以及进度标记
- `/agent-movement-and-suite-with-count`：加入**计数项**[Count]，即乐章内部任何可数的最小单元（涉及的文件、修掉的 bug、写好的测试）。此时乐章写作 `a\b🧩c`：`a` 是已完成的计数项数，`b` 是计数项总数，`c` 是乐章编号，例如 `9\12🧩2` 表示第 2 个乐章的 12 个计数项已完成 9 个。计数项只用来衡量进度，绝不会在计数项处停下
- `/agent-files-and-folders`：新文件用 kebab-case（短横线）命名，文件夹用 PascalCase 命名，带日期的名称以日期开头；计划文件的名字就来自这套规则
